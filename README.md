# Цири ВПН: сайт и проверка узлов

Сайт лежит на GitHub Pages. Раз в 5 минут GitHub Actions запускает `checker/checker.py`, который проверяет узлы и пишет `status.json` в отдельную ветку `status-data`. В файле нет адресов и портов: только название, страна, статус, пинг, аптайм за 24 часа и полоса за сутки. Страница читает этот файл и показывает «Доступность узлов».

Адреса узлов хранятся в секрете репозитория (Secrets), а не в коде.

## Установка

1. Создайте на GitHub **публичный** репозиторий и загрузите в него всё содержимое этой папки. Репозиторий должен быть публичным: в частных репозиториях запуск каждые 5 минут съест бесплатный лимит минут Actions, а адрес файла из ветки `status-data` работает только у публичных.

2. Включите Pages: **Settings → Pages → Build and deployment → Deploy from a branch**, ветка `main`, папка `/ (root)`.

3. Добавьте секрет со списком узлов: **Settings → Secrets and variables → Actions → New repository secret**.
   - Имя: `CIRI_NODES`
   - Значение: JSON-список по образцу из `checker/nodes.example.json`, с вашими адресами и портами.

   Порт указывайте тот, к которому подключаются клиенты (чаще всего 443). Если на узле только UDP-протоколы, TCP-проверка не подойдёт: проверяйте любой открытый TCP-порт. Пример проверки по HTTP(S): `{"id": "pl-1", "name": "Польша", "country": "PL", "host": "...", "port": 443, "check": "http", "path": "/", "tls": true}`. Ответ с кодом ниже 500 считается «работает».

4. Сделайте первый запуск: **Actions → Проверка узлов → Run workflow**. После успешного запуска появится ветка `status-data` с файлами `status.json` и `state.json`. Если запуск упал с ошибкой 403 при публикации, включите **Settings → Actions → General → Workflow permissions → Read and write permissions**.

5. Подключите статус к странице. В `index.html` найдите строку `var STATUS_URL = "status.json";` и замените её на:
   ```
   var STATUS_URL = "https://raw.githubusercontent.com/ВАШ_ЛОГИН/ИМЯ_РЕПО/status-data/status.json";
   ```
   Закоммитьте изменение. Через минуту-две сайт покажет реальные узлы вместо демо-данных.

## Что важно знать

- GitHub запускает расписание не всегда вовремя: задержки в 10–20 минут случаются. Из-за этого и из-за кэша GitHub на файлы (около 5 минут) статус на сайте может отставать от реальности. Если данные старше 30 минут, страница сама покажет предупреждение.
- Если в репозитории долго нет изменений (около 60 дней), GitHub может отключить расписание. Тогда зайдите в Actions и включите workflow заново.
- Проверка идёт с серверов GitHub, адреса у них меняются. Если на узлах стоит fail2ban или лимит подключений, добавьте исключение или не считайте такие проверки атакой. Для этой проверки достаточно открыть и закрыть соединение.
- Пинг считается от сервера GitHub, а не от пользователя. Он показывает, жив ли узел, а не скорость для конкретного человека.
- Статус узла: «работает», если соединение прошло быстрее `slow_ms` (по умолчанию 400 мс), «медленно», если дольше, «недоступен», если не удалось ни с одной из попыток. Пороги меняются в `checker/settings.json`.

## Уведомления в канал статуса (по желанию)

Скрипт может писать в Telegram, когда узел падает или поднимается. В сообщении только название узла, например «Узел «Польша»: недоступен». Сообщение уходит после двух одинаковых проверок подряд, чтобы единичный сбой сети не засорял канал.

1. Создайте бота в @BotFather и добавьте его администратором в канал статуса.
2. Добавьте секреты `TG_BOT_TOKEN` (токен бота) и `TG_CHAT_ID` (например `@cirivpn_status`).
3. В `checker/settings.json` поставьте `"telegram_notify": true`.

## Проверка вручную

Для теста на своём компьютере:

```bash
CIRI_NODES='[{"id":"t","name":"Тест","country":"PL","host":"127.0.0.1","port":22}]' \
CIRI_OUTPUT=/tmp/status.json CIRI_STATE=/tmp/state.json \
python3 checker/checker.py checker/settings.json && cat /tmp/status.json
```
